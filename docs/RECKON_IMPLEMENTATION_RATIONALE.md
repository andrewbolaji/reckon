## Architecture and data flow

`ingest/extractors/{aria_calls,stripe_payments,mongo_jobs}.py` generate or read source records → `ingest/lake.py` writes them to the data lake (local disk or S3, delete-then-write per partition day) → `ingest/loader.py` loads lake files into warehouse `"raw".*` tables as all-text columns, again delete-then-insert per window → `transform/models/staging/*.sql` casts and cleans into `staging.stg_*` → `transform/models/marts/*.sql` aggregates into `marts.mart_*` → three independent readers: `api/main.py` (hardcoded SELECTs, full-privilege DB user, no auth), `copilot/tools.py` (via `reckon_reader`, gated by `copilot/trust_gate.py`), and Metabase (out of scope here). `orchestration/assets_ingest.py` + `assets_dbt.py` wrap the whole extract→load→transform chain as one Dagster asset graph (`orchestration/definitions.py`), fusing dbt's `source()` nodes onto the ingest assets that produce them so a broken source visibly halts its dbt children instead of silently starving them of fresh data. `orchestration/sensors.py` reports daemon-owned run outcomes through `ingest/telemetry.py`; the tagged non-daemon path reports its own outcome through `orchestration/report_run.py`. Both paths push non-fatally to the same Prometheus Pushgateway.

Source of truth for "is the data current": `_loaded_at` on `"raw".*` tables, set by the loader at load time, not event timestamps: checked independently by `copilot/trust_gate.py::check_freshness`, `api/main.py::classify_age`, and Dagster's `FreshnessPolicy` on mart asset specs (`orchestration/assets_dbt.py:27-36`). These three do **not** share a code path; they share only hand-copied threshold constants, one of which (dbt's own `source freshness` block) is never actually invoked by anything in this repo (see Invariants).

Transaction boundary: none spans more than one SQL statement. Each DELETE and each INSERT in `ingest/loader.py:90-101` commits independently under `conn.autocommit = True` (line 84); there is no explicit transaction wrapping a partition's delete-then-insert.

**Deployment topology and config flow.** Two environments run the same application code through different infrastructure. Locally, Compose runs Postgres, Mongo, a one-shot pipeline, persistent Dagster services, API, production-built Nginx dashboard, Metabase, and optional observability. In the cluster, Terraform provisions VPC, EKS, Redshift Serverless, S3, ECR, and IAM. Helm installs API and dashboard Deployments, Mongo, a pipeline CronJob, a post-install seed Job, Pushgateway, and ServiceMonitors only when that CRD exists.

Warehouse config flows from Terraform outputs and shell environment into a standalone Kubernetes Secret through stdin. Helm stores only its name and non-secret resourceVersion, and pods consume it through `envFrom`. Monitoring SMTP and Grafana credentials still use Helm `--set-string`; that accepted limitation is documented below.

Environment-specific wiring is now explicit: the Nginx dashboard proxy receives `API_UPSTREAM` from Compose or Helm; Compose gates API startup on the seed container; Helm gates install completion on the post-install seed Job; Dagster limits local concurrency; Kubernetes forbids overlapping CronJob runs. One meaningful divergence remains: the local `reckon_reader` role is not created on Redshift, so the cloud API continues to use the warehouse admin credential.

## Security and privacy

- **Identity and authorization:** `api/main.py` has none: no auth dependency, API key, or session check on any of its 6 routes, combined with `CORSMiddleware(allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])` (`api/main.py:48-53`). The copilot is not itself network-exposed (`copilot/server.py:193`, `transport="stdio"` only); its access model is "whoever can spawn the MCP process." The `reckon_reader` role exists and is used by the copilot (`copilot/db.py:17-18`); the API does **not** use it: `api/main.py:31-38` connects with the same full-privilege `POSTGRES_USER` the copilot's admin connection uses. Combined with no auth, the one public HTTP surface in this stack runs with admin DB credentials.
- **Tenant isolation:** none, and none appears to be intended: single database, single set of marts, no tenant column anywhere reviewed. Not a defect given the project's apparent scope, but there is nothing to fall back on if that scope changes.
- **Input/output trust boundaries:** API routes take no parameters, so there's no live injection surface today. Copilot's three typed tools (`revenue_summary`, `call_funnel`, `job_completion`) correctly parameterize with `%s` placeholders (`copilot/tools.py:131-136,230-235,306-308`). `query_marts` is the one tool that accepts free-form LLM-authored SQL, and its two safety-regex layers both have confirmed, reproduced gaps (see Invariants table).
- **Sensitive data:** raw schema carries `customer_email` (`ingest/extractors/stripe_payments.py`, synthetic data); marts are aggregated and contain no PII in any query reviewed. No PII reaches logs in `copilot/audit.py` (logs tool name, SQL text, error text, timing: the SQL text itself could theoretically contain a filter value with PII if a user typed one into a copilot conversation, not verified either way here).
- **Secrets and external services:** all DB credentials come from env vars with hardcoded dev-value fallbacks (`api/main.py:33-37`, `copilot/db.py:17-21,24-28`): a misconfigured deployment fails open to a known weak credential rather than refusing to start. Separately, `warehouse/init/01_create_schemas.sql:10` commits a plaintext password (`reckon_reader_dev`) to source control; it only ever runs against the local dev Postgres container (`docker-compose.yml:34` mounts it into `docker-entrypoint-initdb.d`, never referenced by any Redshift/prod path), but it's still a literal committed secret, which is what this codebase's own convention (documented in the author's prior instructions to this assistant) says not to do even for a dev value.
- **Known abuse cases:** unauthenticated bulk read of all business analytics via the API (no control); unbounded-row `query_marts` result via a fake-`LIMIT` comment (control bypassed, only the 5s timeout limits blast radius); `raw`/`staging` read via a quoted schema identifier (regex control bypassed, DB-role backstop untested in CI); connection-pool exhaustion via repeated DB errors against the unauthenticated, wildcard-CORS API (no control, `api/main.py:56-63` leaks on every exception); audit-log misconfiguration turning into a full copilot outage (`copilot/audit.py:9-13` opens the log file unguarded on every call, no catch anywhere it's called).

### Infrastructure security

- **Warehouse Secret handling is fixed; monitoring credentials remain a compromise.** The warehouse password is never expanded by Make, never appears in `kubectl` or Helm arguments, and never renders into the chart or its release history. It is streamed through stdin into a standalone Secret. The monitoring target still injects SMTP and Grafana credentials with Helm `--set-string`, so those values remain in Helm release values/history. That is documented rather than expanded into a second secret-management subsystem for this demo.
- **Every container runs as root with no securityContext (verified this session).** Grepped `infra/helm/reckon/templates/` for `securityContext`, `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation`, `capabilities`, and `seccompProfile`: **zero hits for all six**. None of the three Dockerfiles has a `USER` directive, so all run as uid 0. This combination would be rejected outright by the `restricted` Pod Security Standard.
- **AWS access is granted through the node role rather than a pod identity.** `infra/terraform/iam.tf` attaches bucket-scoped read, write, and delete rights to the EKS node role, and the IMDS hop limit allows pods to obtain it. Only the pipeline needs lake access, but every application pod on those nodes inherits the same potential principal. Combined with root containers and public services, a pod compromise can become data-lake deletion.
- **Nothing is published: the three LoadBalancers are now ClusterIP, and the Grafana password fallback is gone.** API, dashboard, and Grafana were all `type: LoadBalancer` on plain HTTP with no Ingress, no ACM certificate, and no authentication in front of them, and `make monitoring` silently fell back to the committed password `reckon-admin` when `GRAFANA_ADMIN_PASSWORD` was unset. All three are now `ClusterIP`, reached by `kubectl port-forward`, and `make monitoring` exits non-zero rather than installing under a password this repository publishes. This closes the exposure rather than mitigating it: with no public address, the missing TLS, missing API auth, and use of the `reckon_admin` warehouse role are no longer reachable by anyone outside the cluster. They remain real prerequisites for any future internet-reachable deployment. Inside the cluster the boundary is still weak: zero NetworkPolicies exist, so in-cluster Mongo (which sets no `MONGO_INITDB_ROOT_*` and therefore has no authentication at all) and the Pushgateway are reachable from any pod.
- **The dashboard is now a production build, but the container still runs as root.** A multi-stage image uses `npm ci`, runs Vite's production build, and serves only `dist/` through Nginx. `allowedHosts: true`, HMR, and source-serving exposure are gone from the deployed path. Container hardening remains deferred with the other Pod Security controls.
- **The EKS API server is public with no CIDR restriction.** `infra/terraform/eks.tf:14` sets `endpoint_public_access = true` and omits `public_access_cidrs`, which defaults to `0.0.0.0/0`. Authenticated, but reachable from anywhere. Relatedly there is no `access_config` block and no `aws_eks_access_entry`, so the cluster is administrable only by the exact IAM principal that ran `terraform apply`; if that principal is deleted or was an ephemeral role, nobody can `kubectl` in again.
- **At-rest and in-transit gaps.** No `encryption_config` (KMS envelope encryption for Kubernetes Secrets) and no `enabled_cluster_log_types` on the cluster, no VPC flow logs, and no `require_ssl` parameter on the Redshift workgroup with no `sslmode` anywhere in the Python, so psycopg2's default `sslmode=prefer` applies: TLS if offered, silently plaintext if not, never certificate-verified. Traffic stays inside the VPC, so this is low severity, but it is an assumption rather than a control.
- **Local compose publishes stateful services on all interfaces.** `docker-compose.yml:30-31` publishes Postgres on 5432 with the password `reckon_dev`, and `:43-44` publishes Mongo on 27017 with no authentication, both on `0.0.0.0` rather than `127.0.0.1`, so both are reachable from the local network. The Makefile's Dagster targets only need localhost.
- **Nothing destructive is gated by environment.** `var.environment` (`infra/terraform/variables.tf:13-17`) is consumed only as a tag; setting it to `"prod"` leaves `force_destroy` on S3, `force_delete` on ECR, and the absence of any Redshift final snapshot or `prevent_destroy` lifecycle block exactly as permissive. A single `terraform destroy` discards the data lake and the warehouse with no recovery point.

## Performance, scale, and cost

- **Expected workload:** demo-scale: ~150-200 records per source per 30-day window (`ingest/extractors/stripe_payments.py:37`, default `n=150`). Nothing in the reviewed code targets or was tested at higher volume.
- **Potential limiting resources:** S3 full-refresh mode never deletes prior objects, relying on "read only the max key" for correctness (`ingest/lake.py:155-183`): unbounded object growth per full refresh, which the one S3 lifecycle rule that exists does not bound (see "Unbounded growth" below). `dashboard/src/components/ServiceTable.jsx:9` spreads an array into `Math.max(...)`, which has a V8 argument-count ceiling; harmless at current data volume. Four independent `getComputedStyle`/`MutationObserver` instances re-read on every theme toggle (`useThemeColors.js`) rather than one shared subscription: measurable only at a scale this app isn't at.
- **Measured evidence:** not measured. No benchmark, load test, or query plan exists anywhere in the reviewed files or was produced in this review. Per this template's own instruction, scalability is explicitly **not** claimed from the code inspection performed here.
- **Budget:** `README.md:224-228` states roughly $3-5 for a full stack-hour and prescribes "stand it up, verify, screenshot, tear it down." The infrastructure genuinely supports that workflow, with three qualifications below. No dollar figures beyond the repo's own are asserted here.
- **What bills continuously while the stack is up:** the EKS control plane; 2x t3.medium nodes and their EBS root volumes; the single NAT gateway (`infra/terraform/vpc.tf:71-77`), which charges hourly **plus** per-GB processing on every byte the pipeline writes to S3 and every byte of every ECR image pull, because no VPC endpoints exist (a gateway endpoint for S3 is free and would remove most of that); and Redshift Serverless storage. The three LoadBalancers are gone now that every service is `ClusterIP`, which removes three hourly ELB charges from the idle cost. Redshift **compute** bills only per-second while queries run, which is the choice that makes an idle demo cheap and is the single best cost decision in the layer.
- **Three qualifications on the README's estimate.** (1) EKS now defaults to Kubernetes 1.35 in standard support and AL2023 amd64 nodes, but no real account apply verified the control-plane or add-on path. (2) The one NAT gateway plus zero VPC endpoints means transfer cost scales with pipeline volume. (3) There is no TTL, budget alarm, or auto-shutdown, so a forgotten stack bills indefinitely.
- **Unbounded growth:** the S3 data lake, for two compounding reasons. Versioning is enabled (`infra/terraform/s3.tf:10-15`) but the single lifecycle rule (`:34-47`) only transitions current objects under `raw/` to STANDARD_IA at 90 days, with **no** `noncurrent_version_expiration`, no `expiration`, and no `abort_incomplete_multipart_upload`. Meanwhile `ingest/lake.py` deletes without a `VersionId` on every windowed run, which under versioning creates a delete marker and retains the old object forever, and full-refresh runs write a new timestamped key per run and never delete. So every backfill leaves a permanent, fully billed layer that does not even appear in `ListObjectsV2`. Separately, transitioning many small JSON objects to STANDARD_IA (128 KB minimum billable size per object, plus a per-object transition charge) can cost more than leaving them in STANDARD, so the one lifecycle rule that exists may increase the bill rather than reduce it. ECR is correctly bounded by a keep-last-10 policy (`infra/terraform/ecr.tf:20-36`).
- **Cluster sizing is tight but plausible.** Summing declared requests for kube-prometheus-stack plus the application workloads against 2x t3.medium leaves real but limited headroom, and there is no `PriorityClass`, so under memory pressure the kubelet may evict the API as readily as the Pushgateway. Not measured under real scheduling.
- **Metrics are still ephemeral, but their window now matches the control.** Cluster Prometheus retains 72 hours, enough to inspect the 48-hour freshness threshold. A pod restart still loses that history; the absent-metric branch is therefore the primary control after a restart.

## Rollout, rollback, and operations

**Deploy and migration order.** `make up` runs `init`, `infra`, `images`, `kubeconfig`, `monitoring`, and `helm-install` serially; `.NOTPARALLEL` prevents an accidental `make -j` race. ServiceMonitor resources render only when the CRD is available, so `make deploy` no longer depends on monitoring already existing. The post-install hook runs the full pipeline once and Helm waits for it before returning success. dbt still owns warehouse schema creation; the cloud path still has no `reckon_reader` role.

**Guided, not unattended.** `make up` intentionally leaves Terraform approval interactive and requires `redshift_admin_password` in `terraform.tfvars`. README now says so. Once approved, the seed Job is automatic; `make pipeline-run` remains only a manual rerun tool.

**Healthy signals.** `/health`, `/api/freshness`, and three Grafana dashboards remain. `/health` is still a process check rather than a warehouse check, but install success now also requires the seed Job to finish. Prometheus retains 72 hours. Run and dbt failures fire immediately; missing or older-than-48-hour freshness holds for five minutes before firing.

**Rollback and forward recovery.** Helm rollback now points to immutable commit-SHA images, so it can restore a prior application version. It remains manual, with no canary or blue/green path. Data rollback remains a full deterministic pipeline rerun; S3 and Redshift still have no protected recovery point under this disposable-demo posture.

**Runbook docs:** `README.md`, `docs/HANDBOOK.md`, `CLAUDE.md`, and `make help`. README now describes three alerts, guided deployment, automatic seeding, and the external warehouse Secret accurately.
